## 2. Foundational causal mechanisms
Linux container namespaces and cgroups isolate views and resources while sharing a kernel; images are immutable layered root filesystems, container writable layers ephemeral, containerd executes containers via CRI and an OCI runtime. Kubernetes Pod is a scheduling unit with shared IP/network namespace and volumes; container processes in one Pod use localhost and different ports. Pods are not VMs and not interchangeable with Services. Scheduler binds a Pod to a suitable node; kubelet observes binding and uses runtime/CNI/CSI. The scheduler does not start a container or allocate an AWS IP itself. ipamd maintains ENI/IP pools; CNI ADD configures per-Pod network. Readiness influences ready endpoints; liveness restarts a container; startup delays the other probes. A Deployment reconciles a ReplicaSet which reconciles Pods; events are asynchronous, not a synchronous serial RPC from kubectl to every component. A successfully persisted Deployment can exist before any Pod runs.

Requests drive scheduling and HPA CPU-utilization denominators; CPU limits throttle, memory limits can OOM-kill. ConfigMap/Secret environment variables require new container execution to change; mounted updates are eventually reflected subject to application reload and subPath limitations. Base64 Secret storage is not encryption. EKS control-plane protection/encryption does not permit exposing Secrets to broad RBAC readers. Do not put real secrets into manifests, Git or narration. Startup timing and termination grace matter to LB draining.

## 3. Managed architecture and ownership
EKS manages an isolated Kubernetes control plane: at least two API server instances and three etcd instances across three Availability Zones (S60). The two-AZ customer worker VPC does not limit the AWS-managed control plane to only two AZs. AWS patches/operates that managed control plane and backs its internal state; customers do not SSH into API servers/etcd or copy EKS etcd snapshots directly. ENIs created in chosen customer subnets provide control-plane connectivity to workloads/kubelets/webhooks. Control-plane HA does not create multi-AZ application replicas or make AZ-bound data portable. Customer responsibility includes IAM/RBAC, network policy, worker configuration/upgrades, applications/images, availability, data backups, add-on/controller versions and costs. Managed node groups automate lifecycle but are not automatically patched just because control plane upgrades. Self-managed nodes require more bootstrap/lifecycle responsibility. Use AL2023-compatible managed AMIs, not new AL2 node groups or legacy bootstrap.sh assumptions.

## 4. Management access and four identities
**Human**: AWS CLI `eks:DescribeCluster` gets endpoint+CA for kubeconfig; kubeconfig exec runs `aws eks get-token` with selected role credentials; signed STS GetCallerIdentity token authenticates IAM identity to Kubernetes. Do not animate kubectl sending the AWS secret access key to etcd. TLS, endpoint reachability and DNS precede authentication; EKS access entry maps principal; Kubernetes RBAC and EKS access policies are separate additive authorizers (neither is a deny policy engine). API accepts only when authorized. EKS namespace-scoped access-policy names are not Kubernetes Roles; RBAC groups allow custom namespace Roles. `kubectl auth can-i` does not necessarily enumerate EKS-policy grants via `--list`; test the actual operation. 401 is invalid auth/mapping, 403 is denied authorization, timeout is often routing/DNS/filter. Node IAM is not human admin IAM. kubectl is not SSH.

**Node**: EC2 trust `ec2.amazonaws.com`; EKS worker policy, ECR pull permissions and EKS Auth Pod Identity permission; kubelet node identity for Kubernetes. Keep CNI EC2 allocation policy on separate aws-node workload role, not every node. IMDSv2 required, hop limit 1 in this teaching stack to reduce access from ordinary Pods; hostNetwork Pods still require security consideration. No SSH key or remoteAccess block. Node role is not application S3 role.

**Workload**: Pod serviceAccount selects either Pod Identity association or IRSA role, not AWS permissions stored inside a Kubernetes ServiceAccount. Pod Identity: projected token and SDK container-credentials endpoint → local agent 169.254.170.23:80 → EKS Auth AssumeRoleForPodIdentity over HTTPS → temporary credentials → signed AWS API call. Role trust uses pods.eks.amazonaws.com with sts:AssumeRole/sts:TagSession and session tag constraints. Agent's node permission is eks-auth:AssumeRoleForPodIdentity. Supported SDK/default chain required; earlier env/static credentials can override. Private-only egress needs eks-auth endpoint. IRSA: OIDC issuer/provider+audience sts.amazonaws.com+exact namespace/serviceaccount subject, SDK AssumeRoleWithWebIdentity to regional STS; OIDC provider creation is control setup, not an in-path packet gateway. IRSA DNS from private-only VPCs can require external/split-horizon resolver during setup; no insecure thumbprint guessing.

**Controller**: LBC's service account gets an independent IAM role scoped by official release policy (and optional VPC/tag constraints), not node-admin role. CSI controllers also have dedicated IAM. They watch Kubernetes intent and call EC2/ELB APIs; application packets do NOT transit controller Pods or the Kubernetes API. Broad actions required by provisioning controllers are not “least privilege proved”; explain unavoidable read `Resource:*`, official managed-policy scope and opportunities to tighten after testing. Human iam:PassRole must be limited to named cluster/node/workload roles and corresponding PassedToService, not iam:*.

Endpoint strategy: initial public+private, public restricted to learner's actual egress /32; nodes resolve/use private endpoint. Cluster SG controls private endpoint and kubelet connectivity, not public endpoint CIDR restriction. EKS-created private DNS zone needs VPC DNS flags; it is not visible as a normal user-created hosted zone and API endpoint is not a conventional com.amazonaws.region.eks interface endpoint. Fully private step requires tested in-VPC runner/VPN with TCP443 cluster SG allowance and DNS BEFORE disabling public. NAT alone does not let laptop initiate into private API. Enabling a conventional EKS service interface endpoint only covers AWS EKS management API, not private Kubernetes API reachability.

## 5. Routing and Service model
Real decisions must be visually labeled with their engine:
1. **Linux route/rule lookup**: Pod eth0 default → host veth, host routes and policy routing select proper ENI/local veth. Same-node route to Pod C stays on node. Show illustrative host /32 veth route and subnet-connected routes, not claim exact ip rule priority without observation.
2. **VPC route table** at subnet egress: destination 10.42.32.101 matches 10.42/16 local over /0 NAT. No invented per-Pod VPC routes required. Local delivery across AZ subject to SG/NACL. No tunnel or VXLAN in canonical path.
3. **Service selection** in kube-proxy-programmed netfilter: 172.20.10.20:80 is rewritten to selected ready endpoint 10.42.32.101:8080. This is DNAT/connection tracking, NOT a VPC route lookup. ClusterIP is virtual, not an ENI, LB or routable CIDR announcement. Service CIDR never gets a VPC /16→node route in this lab.
4. **LB listener/rule/target selection**: ALB HTTP route/health or NLB flow hashing selects target; not longest-prefix routing. Health/EndpointSlice readiness are related but separate checks. API/controller traffic is a different flow.
5. **IAM/RBAC/filter**: identity/action/policy or L3/L4 allow-state, not route rows.

Canonical iptables path is explicitly verified after addon startup by kube-proxy ConfigMap/logs; package aborts this lecture track if unexpected proxy mode. EKS supports a per-node kube-proxy addon on EC2, but that alone doesn't prove every version/mode. Upstream Linux iptables Service implementation uses kernel rules, not a userspace proxy carrying each packet. Modern alternatives nftables/IPVS exist; don't switch to native nftables merely because host iptables uses nft backend. Those are different concepts. S26/S38 support canonical iptables teaching; observe actual runtime configuration before asserting a deployment uses it.

Normal Pod→ClusterIP cross-node flow: PodA:49152→VIP:80; host Service DNAT to PodB:8080; route selected for PodB; VPC local; PodB sees PodA IP for this internal non-hairpin flow. Reply PodB:8080→PodA:49152 via local route; source node conntrack reverses DNAT so client sees VIP:80. Hairpin/host-originated/external NodePort may require masquerade; do not promise all Service paths preserve source. Same-node ClusterIP uses local host path after DNAT, not VPC.

DNS: Pod uses resolv.conf nameserver 172.20.0.10 UDP/TCP53; service translation selects CoreDNS Pod; CoreDNS answers cluster-local Services from Kubernetes watch cache; it does not make an API round trip for every DNS question. External names forwarded to VPC resolver, with TCP fallback; negative caching/search ndots can explain delays. DNS query/answer and subsequent app connection are distinct flows. Headless service returns endpoint addresses; it doesn't use ordinary VIP balancing.

## 6. CNI, egress and IPv6
Secondary-IP mode attaches IPs to ENIs and assigns to Pods; warm resources improve start speed but consume subnet IPs even if idle. WARM_ENI_TARGET defaults differ from WARM_IP_TARGET/MINIMUM_IP_TARGET use; don't tune all knobs blindly. Prefix delegation uses contiguous /28 IPv4 prefixes on supported Nitro instances; each prefix consumes an ENI IP slot but offers 16 IPs, increasing density within kubelet/max-Pods limits. More free IPs scattered through a fragmented subnet does not guarantee free /28; reserve contiguous ranges. Migrating prefix mode requires compatible CNI and node rotation/max-Pods recalculation; workload capacity constrained by CPU/memory, ENI quotas, per-type max and IP budget. Custom networking allocates Pod ENIs from alternate subnets via ENIConfig per AZ; doesn't create an overlay and can alter SG behavior. SGP uses trunk/branch ENIs and has mode-dependent SNAT, instance-type and NodePort limitations. The primary lab does not enable prefix/custom/SGP by default; demonstrate read-only inspection and a separately planned upgrade, not an unreviewed live CNI mutation.

Default IPv4 VPC CNI: outside associated VPC CIDRs, ordinary Pod source SNAT to node primary IP before VPC forwarding; private subnet /0 NAT; NAT source translated to NAT private address, IGW maps that to allocated EIP on Internet leg. Return follows IGW mapping and NAT state, node conntrack reverses node SNAT to Pod. NAT is outbound connection state, not inbound publication. `AWS_VPC_K8S_CNI_EXTERNALSNAT=true` changes who SNATs; do not animate default node SNAT when that option is on. SGP strict/standard changes which source/SG apply; explicitly separate variants. NAT gateway doesn't apply a security group; it resides in subnet with route/NACL.

Private AWS: interface endpoint private DNS resolves service hostname to VPC ENI; VPC local route + endpoint SG allow TCP443, endpoint policy plus IAM allows action. ECR private pulls need ecr.api + ecr.dkr interface endpoints AND S3 layer downloads (S3 gateway route/policy) with DNS. Public registries/images still require external access or private mirror. STS regional endpoint for IRSA; EKS Auth for Pod Identity; EC2/ELB/logs/SSM etc endpoints only when used. S3 prefix-list route is more specific than default; use AWS-managed actual prefix list, no guessed S3 IP ranges. PrivateLink does not automatically authorize or encrypt application traffic beyond its normal TLS protocol.

IPv6 is a **separate creation-time family**, not flipping existing IPv4 serviceCIDR. EKS IPv6 assigns IPv6 Pod/Service addressing with VPC CNI prefix delegation (EC2 Nitro requirements); /80 per-node prefix in documented tracks; VPC/subnets need IPv6 allocations and IPv6 route/SG/NACL entries. In Standard VPC CNI IPv6 clusters, Pods also have a host-local IPv4 address (not reported as their Kubernetes Pod IP); calls to external IPv4 use this address and CNI SNAT to the node primary IPv4. Pod/Service Kubernetes addresses remain IPv6 only; EKS does not support dual-stack Pods/Services. IPv4 Internet traffic from private nodes may then use the ordinary IPv4 NAT path; don't draw IPv4 NAT gateway as translating IPv6 unchanged. Egress-only IGW differs from NAT and does not convert IPv6 to IPv4; DNS64/NAT64 is an explicit different design, not canonical. Public IPv6 API endpoints created after October 2024 are dual-stack with api.aws format. No runnable IPv6 conversion script supplied; this is an isolated optional architecture/lab stage. S44 is authoritative variant detail.

## 7. Exposure, LB paths, source IP, DNS/TLS
Canonical app uses unprivileged HTTP 8080 and internal ClusterIP80; port-forward binds localhost by default, not public admin. First LBC examples create **internal** ALB and NLB. Testing requires in-VPC runner/approved VPN. Internet-facing extension requires explicit operator intent plus real /32 allowed source; never expose API or admin app. LBC class Ingress `alb`/controller ingress.k8s.aws/alb; Service loadBalancerClass `service.k8s.aws/nlb`. Auto Mode NLB `eks.amazonaws.com/nlb` and IngressClass controller `eks.amazonaws.com/alb` are separate ownership; neither installed/assumed in Standard lab.

ALB IP: browser HTTPS443→ALB listener; TLS terminates at ALB; host/path rule/healthy target selection; NEW backend TCP connection ALB-private-IP:ephemeral→PodIP:8080 over local VPC; return to ALB; ALB replies on client connection. HTTP X-Forwarded-For conveys original client, but socket source at Pod is ALB. Annotations define IP target; endpoint traffic bypasses NodePort/kube-proxy. ALB is proxying two connections, not just destination NAT on one packet. ALB instance: backend connection to NodeIP:NodePort; kube-proxy DNAT to local or cross-node endpoint, possible SNAT depending externalTrafficPolicy; return conntrack then ALB then client. Service must allocate NodePort for instance targets; don't use ClusterIP-only service in runnable instance example. Health port/path must reach actual healthy endpoint. ALB readiness gates can reduce premature rollout routing; LBs have separate target-health delay.

NLB IP: TCP listener→Pod IP target without NodePort; IP target TCP/TLS defaults do not preserve client IP unless enabled (S33); teaching manifest explicitly sets preserve_client_ip.enabled=false to make seen source NLB-private-IP, not client. A preservation-enabled scenario states its constraints and destination topology; UDP/TCP_UDP semantics differ. NLB is not an HTTP proxy with X-Forwarded-For. ProxyProtocol v2 must be supported by the application or it corrupts HTTP preamble. NLB instance targets default preserve client IP, but node externalTrafficPolicy Cluster can SNAT while forwarding; Local restricts ready endpoints to node and preserves client IP with corresponding health/capacity consequences. Don't state Local is a guarantee of evenly balanced capacity across AZs. NLB cross-zone default disabled, ALB behaves differently; inspect explicit LB/target-group attributes and health fail-open conditions before teaching an AZ guarantee. NLB SG source references/health rules must be correct even if transport source is preserved. Allow backend ports from LB SG and LB health checks, not global node-port ranges. Network policies may see translated source; don't filter ALB by raw client ipBlock on backend socket.

TLS exercise: use an owned DNS name; ACM cert in LB region with SANs matching hostname; DNS validation records managed deliberately; Ingress certificate ARN/listen-ports/redirect; Route53 alias A/AAAA as supported to LB DNS/zone, not a fixed A record to current LB node; verify curl hostname certificate/SNI. Re-encryption to HTTPS backend is another connection; configure trust/health deliberately, not an assumed end-to-end client certificate session. No real domain mutation is executed.

Gateway API: as fetched S29, LBC v3.6.2 release; built against Gateway API v1.6.0; HTTPRoute/GRPCRoute→ALB, TCPRoute/UDPRoute/TLSRoute→NLB; L7 >=2.14.0, documented L4 route support >=2.13.3. Do not mix L4/L7 routes on same Gateway; install pinned CRDs/controller extensions and inspect Accepted/ResolvedRefs/Programmed; route attachment/ReferenceGrant permissions distinct from packet forwarding. Do not copy latest main-branch extension CRDs blindly. Auto Mode NOW supports Gateway API (S46): enable `elasticLoadBalancing.gatewayApi.crds.managed`, use eks.amazonaws.com/gateway-alb or gateway-nlb. Auto Mode doc enumerates HTTPRoute/GRPCRoute/TCPRoute/UDPRoute; it does not explicitly establish TLSRoute support here, so mark that unverified rather than assume LBC parity. No default Gateway deployment scripts in this primary lab; extension walkthrough uses pinned prerequisites after compatibility check.

## 8. Filtering and state
Security groups are stateful ENI-associated allow sets; NACLs are subnet stateless ordered allow/deny with default deny and require reverse ephemeral-port allowance. A route existing does not allow a flow. SG allow doesn't bypass Kubernetes network policy or NACL. Same-node Pod traffic does not obligatorily traverse a subnet NACL or a VPC router; don't animate it there. Policy selects application labels and namespace, not an AWS IAM role. Both isolated source egress and destination ingress must allow; rules union, no explicit deny precedence in ordinary NetworkPolicy API. DNS requires TCP and UDP53 permission. Native VPC CNI network-policy agent eBPF needs supported Linux/kernel/addon; manifest alone is inert without enforcement. Standard startup may allow before policy programmed; strict startup initially denies and requires explicit CoreDNS/system allow plan. Lab enables standard-mode native enforcement and uses controller-owned Deployment/ReplicaSet clients, a separately verified source-egress sink, positive DNS and ready-direct-Pod ingress tests. A distinct web-policy Service8080→8080 follows the documented native-CNI equal-port requirement; ordinary F07/F08 Service80→8080 DNAT stays intact and is not policy acceptance. Discover the actual pinned-build agent by its documented image/args, require explicit enablement and readiness on all primary Linux nodes, and inspect managed PolicyEndpoints plus agent evidence before attributing fresh-connection failures to policy; does not falsely promise zero startup window.

**NAT ordering is implementation-dependent at Kubernetes API level** (S27). Use concrete canonical Pod-label→Pod-label path to teach peer identity, and explicitly identify post-DNAT destination/observed source in Service/LB scenarios. For off-VPC IPv4 default CNI node SNAT happens on egress; endpoint SG sees node source for external destinations depending route/SNAT exclusions, whereas same-VPC interface endpoints see Pod source in ordinary canonical mode. Do not assert one universal before/after policy chain ordering across CNI/proxy modes. Test network-policy agent logs, conntrack and packet capture under authorized node access in an isolated lab before claiming specific hooks. HostNetwork/IMDS/node exceptions and existing-connection policy changes require caution. Flow Logs do not prove packet payload, local-veth filtering or API authorization. Denied-flow animation ends exactly at policy decision with no onward token and no fake reverse reply.

## 9. Storage, scale, upgrades and recovery
Standard EBS CSI controller uses its own Pod Identity IAM role (current doc recommends AmazonEBSCSIDriverPolicyV2); node plugin attaches/mounts on EC2; StorageClass ebs.csi.aws.com gp3 encrypted, WaitForFirstConsumer avoids premature AZ binding; PVC reclaim Delete destroys dynamically provisioned disk after claims are released. RWO means read-write by one node, not exactly one Pod; filesystem consistency still matters. Snapshot/restore is separate CSI snapshot controller/CRD plus cloud snapshot and app-consistency workflow, not guaranteed by PVC existence. EFS elastic shared NFS with per-AZ mount targets, SG TCP2049, access-point UID/GID/permissions; EFS CSI dynamic access points on supported EC2; Fargate static only. EFS IAM auth mount options and filesystem policy distinct from provisioning-controller IAM. EBS doesn't become multi-AZ because cluster has two AZs.

HPA asks metrics.k8s.io/custom/external adapters, changes replicas based on configured metrics; metrics-server is prerequisite for CPU HPA and is NOT durable monitoring. Scheduler requests, affinity, taints, Pod topology, available IP/volumes affect placement. CA scales configured ASGs based on unschedulable Pods and simulates templates, not just node average CPU. Karpenter provisions compatible capacity from constraints and can consolidate; IAM, interruption queue and NodePool limits are separately configured. Do not have CA and Karpenter manipulate the same owned nodes. Auto Mode owns its capacity lifecycle and version boundaries; knobs not all identical. PDB gates voluntary eviction, not hardware failure or guaranteed Spot survival; non-evictable workloads/capacity can block upgrade. Spot diversification/multi-AZ and interruption handling reduce risk but don't promise uninterrupted TCP sessions.

Upgrade sequence: read Insights and API deprecations → test app/controllers/addons and backup/restore → plan spare ENI/IP/node capacity and PDB → update one supported minor control plane → wait/verify → compatible addons and canary new node image/replacement (component-specific order depends compatibility matrix) → drain/roll → tests/monitor. MNG does not update automatically with control plane. Record exact versions. As of S01/S50 **EKS supports conditional control-plane rollback to previous minor within 7 days of completed in-place upgrade**, with supported-version/feature/insight/skew constraints. Not arbitrary downgrade; created-at-current clusters and end-of-extended-support auto upgrades not eligible. BEFORE the control-plane rollback, review rollback-readiness insights and application/controller/API compatibility; prepare target-compatible Standard managed/self-managed nodes, then downgrade any incompatible add-ons to target-compatible builds, wait for ACTIVE and validate readiness/function. Self-managed add-ons/controllers need separate compatibility checks. Recheck blockers before CP mutation; final validation repeats these checks rather than postponing them. Auto Mode manages node rollback automatically before CP; Fargate workers cannot be rolled back and affected current-version Pods need the documented removal/redeployment/availability plan. Do not use --force as teaching default. This is not etcd restore and doesn't revert customer state. Fargate pods need separate handling. Older categorical “EKS can never downgrade” is outdated at this research cut.

DR: desired state in version-controlled manifests/IaC, separate recoverable app data snapshots/backups/keys, image registry availability, IAM and network configuration, DNS and external dependencies. Plan RTO/RPO and test restore into separate cluster/account/region as policy requires. Multi-AZ HA is not region DR or ransomware-safe backup. No user-accessible managed etcd snapshot export asserted. Restore app data with consistency checks; roll DNS deliberately; retained EBS/EFS/snapshots/KMS and LB resources can continue billing.

## Audit correction teaching notes (v2)
