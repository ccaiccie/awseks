## s0051 · Config and lifecycle · Config and lifecycle

Chapter four. Configuration and container lifecycle on Kubernetes. ConfigMap and Secret values injected as environment variables are fixed at container start — changing the object does not rewrite a running process environment. Mounted files can update depending on the kube let sync path, but your application must re-read them. Base64 in a Secret is encoding, not encryption at rest; encryption at rest is a separate A P I-server or provider setting. Resource requests drive scheduling and Horizontal Pod Autoscaler signals; CPU limits throttle; memory limits can O O M-kill the container.

## s0052 · Config and lifecycle · Mechanism — config projection

Worked mechanism. A Deployment references a ConfigMap key as an env var and a Secret key as a volume file. Apply updates the objects. New Pods from a rollout see the new env. Old Pods keep the old env until replaced. For files, kube let eventually refreshes the projected volume; the process only notices if it reloads. Never treat base64 visibility in etcd-backed Secret objects as confidentiality against cluster-admin readers.

## s0053 · Config and lifecycle · Probes and drain

StartupProbe delays liveness and readiness until the app finishes slow boot — use it for migrations or JIT warm-up. LivenessProbe failure restarts the container locally; pointing it at a dependency creates restart storms when that dependency blips. ReadinessProbe failure removes the Pod from Service endpoints and load balancer targets without killing it. On delete, terminationGracePeriodSeconds must cover connection drain; align it with target-group deregistration delay so the balancer stops new sends before the process exits.

## s0054 · Config and lifecycle · Observable check — rollout and probes

Observable check. After changing a ConfigMap used as env, confirm the Deployment template still references the ConfigMap, then inspect the running Pod environment separately — get deploy -o yaml shows the template, not the live process. Prefer exec printenv only if the reviewed image has a shell; agnhost is not guaranteed to. Otherwise compare env on a replaced Pod after rollout. Watch `kube control -n eksclass rollout status deployment/web`. Describe a Pod and read Last State for O O MKilled versus probe failures. Failure lab: set a readiness path that 404s and confirm endpoint slice empties while the Pod stays Running; set a liveness path that fails and confirm restarts climb.

## s0055 · Config and lifecycle · Lifecycle lab pointers

Use the digest-pinned app Deployment from scripts/04-app.sh as the base. Adjust probes only in a reviewed overlay. Observe; do not invent a second unpinned image.

## s0056 · Config and lifecycle · Config takeaway

Takeaway. Env needs a new container; base64 is not encryption; requests schedule and limits enforce; readiness gates traffic; liveness is local; drain must match the balancer.

## s0057 · EKS architecture · EKS architecture

Chapter five. Standard Amazon E K S architecture for this class: a managed Kubernetes control plane and customer-owned workers in your virtual private cloud. The managed plane keeps at least two A P I server endpoints and three etcd members across three Availability Zones inside the AWS-managed account boundary. Your worker virtual private cloud may use two Availability Zones; that does not shrink the plane's three-availability zone design. Elastic network interfaces for the plane appear in your subnets so the A P I can reach Pods and kubelets. There is no SSH to etcd and no customer export of managed etcd snapshots.

## s0058 · EKS architecture · Mechanism — shared responsibility

AWS operates A P I servers, etcd, and the managed plane network path. You own node A M Is and kube let skew, I A M and access entries, Kubernetes R B A C, network policy agents, application Deployments, persistent data backups, add-on version choices, and cost. Managed node groups do not silently patch the OS just because the control plane minor moved. Upgrading the plane without preparing workers and add-ons is a skew and webhook risk — covered again in the upgrade chapter.

## s0059 · EKS architecture · Worked example — describe the cluster boundary

Worked example. After scripts/02-cluster.sh in an authorized sandbox, `aws eks describe-cluster --name "$STACK"` shows endpoint private-or-public settings, version, and virtual private cloud config. `kube control get --raw=/readyz?verbose` checks A P I readiness through your kubeconfig — not etcd SSH. Nodes appear only after the managed node group joins. Failure mode: treating plane multi-availability zone as application multi-availability zone, or expecting a user-accessible etcd snapshot for region disaster recovery.

## s0060 · EKS architecture · Architecture takeaway

Takeaway. Plane HA is multi-availability zone inside AWS; workers, identity, policy, apps, and backups are yours. Cluster ENIs live in your virtual private cloud. No etcd export.

## s0224 · DNS and TLS operations · DNS and TLS operations

Chapter sixteen. Public name resolution and transport security for published applications. Route 53 alias records follow the load balancer D N S name and hosted zone — a fixed A record to one current node IP breaks on replacement. Amazon Certificate Manager certificates are regional; request them in the same region as the load balancer and validate with D N S records you own. T L S commonly terminates at the Application Load Balancer; re-encryption to Pods is a deliberate second hop. This class never mutates an example or unowned domain.

## s0225 · DNS and TLS operations · Mechanism — resolver and certificate chain

Mechanism. Browser or client resolver asks public D N S for your FQDN. Route 53 returns an alias answer that tracks the load balancer. The client opens T L S to the balancer; SNI selects the certificate; the SAN must include your hostname. A C M owns private keys for certificates it issues. After T L S terminates at the A L B, the backend connection is a separate decision — cleartext to Pod IP targets, or re-encrypt if you configured it. Security groups and health checks still gate targets independently of certificate validity.

## s0226 · DNS and TLS operations · Worked example — owned domain procedure

Worked example on an owned domain only. Request an A C M certificate in the load balancer region with D N S validation. Create the validation CNAMEs in your hosted zone and wait for ISSUED. Create an alias A or AAAA record to the load balancer D N S name and hosted zone ID — not a guessed node IP. Annotate the Ingress with the certificate ARN and optional HTTPS redirect. Failure modes: certificate in the wrong region; alias pointed at a deleted balancer; security group allowing 443 but health check failing on the wrong path; network policy or network A C L dropping return traffic after T L S succeeds.

## s0227 · DNS and TLS operations · DNS/TLS observation (no unowned writes)

## s0272 · Observability · Observability

Chapter twenty. How you prove what happened. Events, container logs, node logs, control-plane A P I and audit logs, metrics, and traces answer different questions. E K S can ship control-plane logs to CloudWatch when enabled — that costs money and still does not show Pod-to-Pod payload. virtual private cloud Flow Logs show accepted or rejected tuples at elastic network interface boundaries; they are not full local dataplane truth and cannot alone prove a same-node network policy drop. metrics-server feeds H P A; it is not durable monitoring or APM.

## s0273 · Observability · Mechanism — pick the layer
